# Сценарии испытаний

> Статус: черновик формата DSL.

## Текущая реализация

Добавлен первый интерактивный прототип вкладки `Сценарии`: сценарий собирается из
типизированного каталога блоков, валидируется и выполняется пошагово с текстовым
протоколом. Доступны проверки подключений, DISARM, параметра и диапазона тока,
ожидание, подтверждение оператора и текстовый результат. Блоки можно переставлять
и удалять, выполнение можно остановить. Вкладка сначала показывает отдельный список
доступных сценариев. Выбор существующего сценария или команда `Добавить сценарий`
открывает отдельную страницу редактора с командами `Назад`, `Сохранить` и `Запустить`.
На текущем этапе библиотека хранится локально в `localStorage` приложения; версионируемое
файловое или SQLite-хранилище остаётся следующим расширением.

Проверка параметра во время запуска выполняет отдельный `PARAM_REQUEST_READ` и
сравнивает полученный `PARAM_VALUE`, а не значение из UI-кэша. Блок подачи звука
использует динамик компьютера; для него задаются число повторов и интервал.

Текущий исполнитель поддерживает только проверки и действия без управляющего
воздействия. До появления `motor_test`, RC override, записи параметров и других
опасных блоков выполнение должно быть перенесено в Rust Application Core и
подключено к общей state machine, safety interlocks и audit log.

## Цель

Сценарий описывает последовательность действий, условий и измерений. Он не получает прямой доступ к MAVLink, файловой системе или ОС. Все действия выполняются через ограниченный API приложения.

Пользователь должен иметь возможность создавать, редактировать, копировать и запускать такие сценарии непосредственно в интерфейсе приложения. Ручное редактирование YAML допускается как дополнительный инженерный режим, но не является обязательным для обычного оператора.

Сценарии могут использоваться повторно и назначаться разным модификациям БПЛА через профили аппарата.

## Термины

- **шаг** — одно типизированное действие, проверка, ожидание или измерение;
- **сценарий** — упорядоченная последовательность шагов с требованиями и ограничениями;
- **шаблон сценария** — заготовка, из которой создаётся новый сценарий;
- **профиль БПЛА** — параметры конкретной модификации: тип аппарата, контроллер, моторы, назначение каналов, допустимые нагрузки и поддерживаемые операции;
- **запуск сценария** — неизменяемый экземпляр сценария и профиля, использованный во время конкретного испытания.

## Визуальный редактор

В приложении предусматривается визуальный редактор сценариев. Пользователь собирает сценарий из каталога разрешённых шагов, изменяет их параметры и порядок выполнения.

Предварительный вид:

```text
Сценарий: Проверка силовой установки — модификация A

1. [Проверка] Подтвердить подготовку стенда
2. [Проверка] Проверить подключение полётного контроллера
3. [Проверка] Проверить подключение амперметра
4. [Команда]  Подать 10% нагрузки на двигатель 1 на 5 секунд
5. [Измерение] Записать ток в течение 3 секунд
6. [Условие]  Ток не должен превышать 15 A
7. [Команда]  Остановить двигатель
8. [Отчёт]   Сохранить результат
```

Основные операции редактора:

- добавить шаг из каталога;
- настроить параметры шага;
- изменить порядок шагов;
- временно отключить безопасный необязательный шаг;
- копировать шаг или весь сценарий;
- создать сценарий из шаблона;
- проверить сценарий до сохранения и запуска;
- сохранить новую версию;
- назначить совместимые профили БПЛА;
- импортировать или экспортировать сценарий.

Опасные обязательные проверки, автоматически добавленные safety-политикой, нельзя отключить в редакторе.

## Предлагаемый формат

На первом этапе — декларативный YAML. Внутри приложения он преобразуется в строго типизированную модель и проходит валидацию до запуска.

Визуальный редактор и YAML являются двумя представлениями одной типизированной модели. UI не должен генерировать произвольный исполняемый код.

```yaml
schema: 1
name: Current sensor calibration
version: 0.1.0

requirements:
  vehicle_connected: true
  vehicle_disarmed: true
  reference_sensor: hall-v1
  operator_confirmation: true

limits:
  max_current_a: 40
  max_step_duration_s: 15
  mavlink_loss_timeout_ms: 1000

steps:
  - snapshot_parameters:
      names: [BATT_AMP_PERVLT, BATT_AMP_OFFSET]

  - measure:
      name: zero
      duration_s: 5
      require_motors_stopped: true

  - motor_test:
      motors: all
      throttle_percent: 15
      duration_s: 8

  - wait_until:
      expression: reference.current.stddev < 0.3
      window_s: 2
      timeout_s: 5

  - measure:
      name: load_15
      duration_s: 5
      signals:
        - reference.current
        - autopilot.current
        - autopilot.voltage

  - calculate:
      algorithm: current_linear_calibration

  - confirm_parameter_changes: {}

  - apply_parameter_changes: {}

  - verify:
      max_absolute_error_a: 0.5
      max_relative_error_percent: 3
```

## Категории шагов

### Подключение и проверка

- `require_connection`;
- `require_vehicle_state`;
- `require_device`;
- `check_parameter`;
- `operator_checklist`;
- `operator_confirmation`.

### Управление

- `rc_override`;
- `release_rc_override`;
- `motor_test`;
- `set_servo`;
- `arm` и `disarm` — потенциально отдельный повышенный уровень разрешений;
- `emergency_stop` — системное действие, не обычный шаг.

### Измерение

- `wait`;
- `wait_until`;
- `measure`;
- `mark_event`;
- `start_recording`;
- `stop_recording`.

### Параметры

- `snapshot_parameters`;
- `read_parameter`;
- `propose_parameter_changes`;
- `confirm_parameter_changes`;
- `apply_parameter_changes`;
- `restore_parameter_snapshot`.

### Анализ

- `calculate`;
- `assert`;
- `compare`;
- `verify`;
- `generate_report`.

## Правила выполнения

1. Сценарий полностью валидируется до начала теста.
2. Все обязательные устройства и сигналы проверяются заранее.
3. Каждый шаг имеет timeout.
4. Опасные команды проходят runtime safety-проверку даже после валидации.
5. Отмена пользователем доступна в любой момент.
6. При ошибке выполняется системная процедура abort, а не произвольный следующий шаг.
7. RC override всегда освобождается при завершении, ошибке или потере связи.
8. Запись параметров требует подтверждения, если политика стенда явно не разрешает автоматическую запись.

## Профили модификаций БПЛА

Сценарий не должен содержать все аппаратные значения напрямую. Отличия модификаций задаются профилями, например:

```yaml
schema: 1
profile: copter-model-a
name: Copter Model A

vehicle:
  type: copter
  firmware_family: ardupilot

mapping:
  motor_under_test: 1
  throttle_channel: 3

limits:
  max_current_a: 40
  max_throttle_percent: 30
  max_motor_run_s: 15

devices:
  reference_sensor: hall-v1
```

Перед запуском приложение объединяет сценарий с выбранным профилем и проверяет:

- совместимость типа аппарата и прошивки;
- наличие необходимых устройств и сигналов;
- назначение каналов и моторов;
- допустимость нагрузки и длительности;
- наличие всех значений, на которые ссылается сценарий.

Ограничения профиля могут только ужесточать системные safety-ограничения, но не ослаблять их.

## Доступность раздела испытаний

Раздел «Испытания» становится доступен, когда приложение имеет хотя бы одно рабочее подключение к известному устройству или источнику данных. Наличие конкретно амперметра не является общим условием: разные испытания требуют разный набор оборудования.

Внутри раздела каждый сценарий проверяет собственный блок `requirements`. Сценарий можно открыть и просмотреть, но запуск блокируется, пока не выполнены именно его требования. Интерфейс должен перечислять отсутствующие подключения или невыполненные условия, например:

```text
Калибровка тока — запуск недоступен
Нужно подключить:
  • полётный контроллер
  • эталонный амперметр hall-v1
```

Таким образом, доступность раздела определяется наличием подключений, а готовность к запуску — требованиями выбранного сценария и safety-состоянием.

## Версионирование и воспроизводимость

Изменение сохранённого сценария создаёт новую версию. Каждый запуск хранит:

- точную версию сценария;
- точную версию профиля БПЛА;
- фактические значения параметров шагов;
- версию приложения и прошивки контроллера;
- подтверждения оператора;
- журнал команд и результатов.

Это позволяет изменить сценарий в будущем, не меняя историю уже проведённых испытаний.

## Будущее расширение

Встроенный JavaScript или Lua можно добавить позднее для вычислений и генерации шагов. Скрипт должен работать в sandbox и обращаться только к безопасному API движка.
