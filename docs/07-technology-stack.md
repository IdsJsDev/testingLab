# Технологический стек и сборка

> Статус: принятое архитектурное решение.

## Решение

Для первой версии приложения выбран следующий стек:

- Tauri 2 — оболочка приложения и связь UI с системным ядром;
- Rust — MAVLink, Serial, safety-контур, движок сценариев, вычисления и работа с данными;
- TypeScript + Preact + Vite — пользовательский интерфейс;
- SQLite — локальное хранение метаданных, результатов испытаний и журналов;
- YAML — редактируемое представление сценариев испытаний;
- uPlot — лёгкие графики телеметрии и результатов измерений.

Приложение не требует отдельного Node.js-процесса, локального web-сервера или поставляемого вместе с ним браузера. Собранный Preact UI встраивается в приложение, а Rust-компоненты компилируются в его исполняемую часть. Tauri использует системный WebView целевой ОС.

## Причины выбора

- небольшой размер дистрибутива по сравнению с приложением, включающим собственный Chromium;
- общий Rust-код для Windows, macOS и Linux;
- пригодность Rust для критической логики, обработки ошибок и конкурентных потоков данных;
- возможность отделить UI от MAVLink-команд и обязательных safety-проверок;
- возможность в будущем добавить Android, сохранив доменную логику и движок сценариев;
- Preact предоставляет компонентную модель, близкую к React, при небольшом runtime.

При выборе UI-зависимостей необходимо проверять их совместимость с Preact. При необходимости допускается `preact/compat`. Для потоковых графиков предпочтительны библиотеки, не зависящие от React runtime.

## Состав приложения

Предлагаемое разделение исходного кода:

```text
apps/
  operator-ui/          Preact + TypeScript + Vite

src-tauri/
  src/                  запуск приложения, команды и события Tauri

crates/
  domain/               состояния, команды и результаты
  safety/               ограничения и централизованный abort
  transports/           общие транспортные интерфейсы
  mavlink-adapter/      MAVLink и особенности ArduPilot
  device-adapters/      датчик Холла и будущие устройства
  script-engine/        типизированный YAML DSL
  calibration/          расчёты и проверки качества
  storage/              SQLite, snapshots и audit log
  simulator/            SITL и симуляторы устройств
```

Конкретная структура каталогов может уточняться при создании каркаса, но границы ответственности должны сохраняться.

## Формат поставки

UI, Rust-ядро, MAVLink, safety-логика и SQLite-библиотека собираются в одно приложение. Отдельная сборка создаётся для каждой целевой ОС:

- Windows — portable `.exe` или установщик `.exe`/`.msi`;
- Linux — один `.AppImage` или нативный пакет дистрибутива;
- macOS — приложение `.app`, распространяемое, например, в одном `.dmg`.

Один универсальный исполняемый файл для разных операционных систем не создаётся. Каждая ОС и аппаратная архитектура получает собственный артефакт сборки.

Рабочие данные не встраиваются в исполняемый файл и хранятся отдельно в пользовательском каталоге приложения:

- база SQLite;
- журналы испытаний;
- отчёты;
- настройки;
- импортированные и экспортированные сценарии.

Это позволяет обновлять или заменять приложение без потери результатов испытаний.

## Целевые платформы

В текущий объём входят:

1. Windows;
2. macOS;
3. Linux.

Сборка и проверка выполняются отдельно для каждой ОС, предпочтительно через CI с нативными runners. Подпись и публикация пакетов зависят от требований конкретной платформы.

## Возможность Android

Android не входит в текущий MVP, но архитектура не должна блокировать его последующее добавление.

Для этого:

- UI не обращается к Serial, USB или MAVLink напрямую;
- все воздействия проходят через Rust Application Core и safety-проверки;
- обмен UI с ядром выполняется типизированными командами и событиями;
- transport API не зависит от способа подключения;
- desktop-реализации используют Serial, TCP и UDP;
- будущая Android-реализация USB использует Android `UsbManager` через платформенный Kotlin-плагин Tauri;
- domain, safety, calibration и script engine остаются общими Rust-компонентами.

Поддержка Android USB host зависит от аппаратных возможностей конкретного телефона или планшета. Перед включением Android в план разработки потребуется отдельный технический прототип с целевым устройством и реальным полётным контроллером.

## Ограничения решения

- системные WebView разных ОС могут иметь небольшие различия в отображении;
- нативные Serial/USB разрешения и драйверы различаются между платформами;
- macOS, Windows и Linux требуют отдельных сборок и проверок;
- Android потребует отдельного платформенного USB-адаптера;
- safety-критические операции запрещено переносить в TypeScript/UI.
