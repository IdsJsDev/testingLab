# Архитектура

> Статус: черновик архитектуры. Технологический стек утверждён в [отдельном решении](07-technology-stack.md).

## Общая схема

```text
┌──────────────── Desktop UI ────────────────┐
│ подключение │ графики │ сценарии │ отчёты │
└────────────────────┬───────────────────────┘
                     │ команды и события
┌────────────────────▼───────────────────────┐
│               Application Core            │
│ state machine │ safety │ scripts │ storage│
└───────────┬─────────────────────┬──────────┘
            │                     │
┌───────────▼──────────┐  ┌──────▼──────────┐
│ MAVLink / ArduPilot  │  │ Device adapters │
│ telemetry, params, RC│  │ Hall, RPM, etc. │
└───────────┬──────────┘  └──────┬──────────┘
            │                     │
     Flight controller       External MCU
```

## Компоненты

### Desktop UI

- управление подключениями;
- отображение текущего состояния стенда;
- просмотр телеметрии и графиков;
- просмотр текущих параметров и сведений о прошивке контроллера;
- защищённое редактирование разрешённых параметров;
- редактор и запуск сценариев;
- подтверждение опасных действий;
- просмотр предлагаемых изменений;
- история запусков и отчёты.

UI не должен напрямую отправлять MAVLink-команды. Все команды проходят через Application Core и safety-проверки.

### Основные разделы интерфейса

Предварительный верхний уровень навигации:

```text
Подключения | Испытания | Телеметрия | Управление | Параметры | Сценарии | Результаты
```

Доступность разделов зависит от состояния ядра и соединений:

- `Подключения` — всегда;
- `Испытания` — при наличии хотя бы одного рабочего подключения, готовность конкретного сценария проверяется отдельно;
- `Телеметрия` — при наличии хотя бы одного источника телеметрии или измерений;
- `Управление` — только при наличии контроллера и разрешённого управляющего маршрута;
- `Параметры` — после подключения контроллера и загрузки его параметров;
- `Сценарии` — всегда, чтобы работать с ними без оборудования;
- `Результаты` — всегда для просмотра сохранённых запусков.

При увеличении числа разделов горизонтальные вкладки могут быть заменены боковой навигацией. Это изменение не должно затрагивать логику доступности.

### Телеметрия

Раздел показывает текущие значения и графики доступных источников:

- heartbeat и состояние контроллера;
- напряжение и ток ArduPilot;
- ток внешнего амперметра;
- RC-каналы;
- режим, arm/disarm и failsafe;
- в будущем RPM, температуры, вибрации и другие сигналы.

Набор виджетов зависит от реально подключённых устройств. Отсутствующий сигнал показывается как недоступный, а не как нулевое значение.

### Параметры контроллера

Раздел отделяет сведения о прошивке от изменяемых параметров.

Сведения о прошивке отображаются только для чтения:

- тип аппарата и семейство контроллера;
- версия ArduPilot;
- идентификаторы системы и компонента;
- capabilities и доступные MAVLink-возможности.

Работа с параметрами предусматривает:

- загрузку фактического списка с подключённого контроллера;
- поиск и фильтрацию;
- показ текущего значения, типа, диапазона и описания;
- редактирование только валидных значений;
- предварительный список изменений `старое → новое`;
- snapshot до первой записи;
- явное подтверждение записи;
- ожидание подтверждения и повторное чтение;
- audit log и возможность контролируемого rollback.

Изменение параметра в UI не отправляет его немедленно. Пользователь сначала формирует набор предлагаемых изменений, затем отдельно применяет его.

Обновление или перепрошивка ArduPilot не входит в первую версию раздела `Параметры`. Если такая возможность потребуется, она проектируется как отдельная операция с собственными проверками и восстановлением после ошибки.

### Application Core

Отвечает за:

- единую модель состояния;
- жизненный цикл теста;
- выполнение сценариев;
- обработку таймаутов и отказов;
- синхронизацию потоков измерений;
- расчёты и валидацию результатов;
- журналирование;
- создание снимков и восстановление параметров.

Предлагаемые состояния:

```text
DISCONNECTED → CONNECTED → SAFE → READY → RUNNING
                                      ↘ ABORTING → SAFE
                                      ↘ FAULT ───→ SAFE
```

### ArduPilot Adapter

Минимальные обязанности:

- ожидание и контроль heartbeat;
- получение версии прошивки и типа аппарата;
- загрузка набора параметров;
- чтение `BATTERY_STATUS` и связанной телеметрии;
- надёжная запись параметров с ожиданием подтверждения;
- отправка `RC_CHANNELS_OVERRIDE`;
- выполнение `MAV_CMD_DO_MOTOR_TEST`;
- arm/disarm только через явно разрешённые операции;
- немедленное прекращение воздействий при abort.

Набор параметров необходимо получать с подключённого контроллера: названия и доступность параметров зависят от типа аппарата и версии ArduPilot.

### Device Adapter

Каждый внешний прибор реализует общий интерфейс:

- идентификация устройства;
- версия протокола и прошивки;
- возможности и единицы измерения;
- запуск и остановка потока данных;
- timestamp измерения;
- health/status;
- сырые и откалиброванные значения.

Первый адаптер — USB Serial для измерительного модуля с датчиком Холла.

### Storage

Предлагается SQLite для метаданных и запусков. Большие временные ряды можно сначала также хранить в SQLite, а при необходимости перейти на отдельный бинарный формат.

Основные сущности:

- `Vehicle`;
- `FlightControllerSnapshot`;
- `Device`;
- `Script` и `ScriptVersion`;
- `TestRun`;
- `SignalSample`;
- `CalculatedResult`;
- `ParameterChange`;
- `AuditEvent`;
- `Report`.

## Технологический стек

Принят стек Tauri 2 + Rust + TypeScript/Preact/Vite + SQLite. Сценарии представлены в YAML, для лёгких потоковых графиков выбран uPlot.

Форматы сборки, причины выбора, границы платформенного кода и условия будущего добавления Android описаны в документе [«Технологический стек и сборка»](07-technology-stack.md).

## Нефункциональные требования

- Windows как вероятная основная платформа; macOS/Linux — уточнить;
- приложение не должно зависать при пропадании устройства;
- остановка теста должна иметь более высокий приоритет, чем обычные команды;
- журнал должен сохраняться при аварийном завершении;
- все измерения должны иметь монотонные timestamps;
- сценарии и отчёты должны иметь версии;
- поведение без реального оборудования должно проверяться через ArduPilot SITL и симулятор датчика.

Предварительная схема USB-, LoRa- и сетевых подключений, а также правила выбора управляющего маршрута описаны в документе [«Подключения и управляющий канал»](08-connectivity-and-control.md).
