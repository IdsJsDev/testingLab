# Пошаговый план разработки

> Статус: рабочий план. Этапы и критерии могут уточняться в процессе разработки.

Основной прикладной процесс зафиксирован в
[`13-motor-test-workflow.md`](13-motor-test-workflow.md). Моторный тест реализуется
поэтапно: сначала backend-контур остановки и ограниченное управление, затем
измерения и только после аппаратной проверки — автоматическая запись параметров.

Приложение разрабатывается небольшими проверяемыми вертикальными этапами. Каждый этап должен заканчиваться работающим результатом и не зависеть от ещё не реализованных возможностей следующих этапов.

## Этап 1 — каркас приложения

Статус: базовый каркас готов.

Состав:

- Tauri 2 и минимальное Rust-ядро;
- Preact + TypeScript + Vite;
- базовый экран подключений;
- типизированная команда UI → Rust для проверки готовности ядра;
- исходное безопасное состояние `DISCONNECTED`;
- unit-тест начального состояния;
- release-сборка приложения без установочного пакета;
- заготовка иконки приложения.

Критерии завершения:

- `npm run build` выполняется успешно;
- `cargo test --manifest-path src-tauri/Cargo.toml` выполняется успешно;
- `npm run tauri build -- --no-bundle` создаёт нативный исполняемый файл;
- приложение не содержит управления оборудованием и не может создать воздействие на моторы.

Перед созданием публичных установочных пакетов потребуется подготовить полный набор платформенных иконок и настройки подписи.

## Этап 2 — подключение полётного контроллера

Статус: в работе. Реализовано обнаружение USB Serial-портов и безопасная проверка входящего MAVLink heartbeat.

Состав:

- обнаружение Serial-портов;
- выбор порта и baud rate;
- подключение по MAVLink;
- ожидание и контроль heartbeat;
- определение system ID, типа аппарата и версии прошивки;
- вкладки телеметрии и параметров с корректными состояниями доступности;
- отображение состояния соединения;
- безопасное отключение и обработка пропадания устройства;
- симулятор или SITL для автоматических проверок.

Результат: приложение стабильно подключается к контроллеру по USB, показывает базовые сведения и обнаруживает потерю связи. Управляющие команды ещё заблокированы.

На этом этапе вкладка параметров работает только на чтение. Защищённая запись параметров добавляется вместе со snapshot и audit log на этапе 7.

Первая аппаратная проверка выполнена на `MatekH743` с ArduPilot. Контроллер определился как составное USB-устройство с двумя CDC Serial-портами. Heartbeat получен через `/dev/cu.usbmodem1101`: system ID `1`, component ID `1`, тип `MAV_TYPE_FIXED_WING`, autopilot `MAV_AUTOPILOT_ARDUPILOTMEGA`, состояние `MAV_STATE_STANDBY`.

## Этап 3 — подключение Arduino-амперметра

Состав:

- описание версионируемого Serial-протокола;
- выбор второго независимого USB-порта;
- идентификация устройства;
- получение тока, timestamp, сырых значений и статуса;
- обнаружение устаревших данных и потери устройства;
- программный симулятор амперметра.

Результат: контроллер и амперметр работают одновременно, а UI показывает здоровье обоих соединений.

## Этап 4 — синхронизация и запись данных

Состав:

- единая монотонная временная шкала;
- синхронизация MAVLink-телеметрии и данных амперметра;
- потоковые графики;
- SQLite;
- запись измерений, подключений и диагностических событий.

Результат: ручной тест создаёт сохранённый запуск с сопоставленными временными рядами.

## Этап 5 — safety-контур и управление

Состав:

- полная state machine;
- ограничения нагрузки и длительности;
- централизованный идемпотентный abort;
- timeout и контроль heartbeat;
- motor test и, при необходимости, RC override;
- сначала SITL, затем контроллер без исполнительных механизмов.

Результат: приложение выполняет ограниченное управляющее воздействие и гарантированно прекращает его при отмене или ошибке.

## Этап 6 — фиксированный сценарий калибровки

Состав:

- проверка готовности стенда;
- измерение нуля;
- несколько ступеней нагрузки;
- ожидание стабилизации;
- запись измерительных окон;
- остановка и сохранение результата.

Результат: один заранее заданный сценарий безопасно и воспроизводимо собирает точки калибровки.

## Этап 7 — расчёт и применение калибровки

Состав:

- предобработка измерений;
- устойчивая линейная регрессия;
- проверки качества;
- snapshot параметров;
- предложение и подтверждение изменений;
- запись, повторное чтение и проверочный тест;
- контролируемый rollback.

Результат: выполнен полный процесс «измерить → рассчитать → применить → проверить».

## Этап 8 — альтернативные управляющие маршруты

Состав:

- LoRa или локальная сеть как первый дополнительный маршрут;
- выбор единственного активного управляющего маршрута;
- проверка доступности маршрута;
- безопасное ручное переключение;
- журналирование маршрута каждой команды.

Результат: управляющие команды могут проходить через основное USB-соединение и один проверенный альтернативный транспорт.

## Этап 9 — пользовательские сценарии и профили БПЛА

Статус: начат прототип редактора и read-only исполнителя типизированных блоков.

Состав:

- типизированный YAML DSL;
- визуальный редактор шагов;
- шаблоны и копирование сценариев;
- профили модификаций БПЛА;
- статическая валидация;
- версии, импорт и экспорт.

Результат: инженер создаёт сценарии в UI и безопасно применяет их к совместимым модификациям БПЛА.

## Этап 10 — отчёты и поставка

Состав:

- локальные отчёты и история запусков;
- графики «до/после»;
- экспорт;
- платформенные иконки;
- установочные пакеты для Windows, macOS и Linux;
- CI-сборки и проверки на целевых ОС;
- настройки подписи релизов.

Результат: оформленный MVP, пригодный для повторяемой эксплуатации и установки на целевые компьютеры.
